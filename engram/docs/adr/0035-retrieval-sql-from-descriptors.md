# ADR-0035 — Retrieval SQL generated from corpus/graph descriptors via a Protocol + ABC seam

**Status:** Accepted (2026-07-09). This seam reshaped engram's retrieval so the reusable stack could be extracted into the `engramai` shared library ([root ADR-0006](../../../docs/adr/0006-engramai-shared-ai-library.md)). Scope: the new `engram.ai.retrieval` descriptors + SQL-builder ABCs (in `engramai`), and engram's `features/serve/{corpus_schema,graph_schema}.py`, `features/serve/search_dialect/{dialect,paradedb,pg_textsearch}.py`, `features/serve/graph_backend/{backend,cte,age}.py`. No schema, `api` SQL *result* surface, or `wiki_reader` role behaviour change — the generated `api.search` / `api.graph_*` bodies return identical results ([ADR-0036](0036-behavioral-parity-generated-sql.md)); only the SQL *text* is now generated rather than hand-written.

**Context.** engram's retrieval read surface — `api.search` (hybrid BM25 + vector RRF) and `api.graph_expand` / `api.graph_paths` (link-graph traversal) — was generated by per-dialect and per-backend code that hand-wrote the *entire* SQL body as a string constant (`_API_SEARCH_BODY`, `_EXPAND_BODY`, `_PATHS_BODY`, `_CREATE_GRAPH_DDL`, `_REFRESH_BODY`). The wiki schema was baked directly into that text: the four searchable surfaces (card / section / claim / raw), the `page_pool` / `raw_keys` facet pools, `wiki.edges`, `api.cards`, and the `EXPAND_COLUMNS` / `PATHS_COLUMNS` RETURNS contract were all literal tokens inside the string.

The dual-dialect BM25 seam ([ADR-0006](0006-dual-dialect-bm25-seam.md)) and the dual graph backend ([ADR-0007](0007-age-multihop-dual-graph-backend.md)) had already abstracted the **DB-engine axis** (ParadeDB `pg_search` vs `pg_textsearch`, recursive-CTE vs Apache AGE) behind Protocol-satisfying adapters. But they left the **corpus axis** baked into the SQL text. Extracting the stack into a domain-general library ([root ADR-0006](../../../docs/adr/0006-engramai-shared-ai-library.md)) forced the inversion: the library cannot name `wiki.edges` or `api.cards`, so the corpus had to become *data* the library generates SQL from.

**Options considered.**

- **Keep hand-written SQL per dialect/backend; duplicate the bodies for a second corpus.** Rejected — the baked-in schema is precisely the leak the extraction exists to remove, and a second corpus would mean a second full copy of every gnarly body.
- **Parameterise only the table/column *names* via string substitution.** Rejected — the searchable surfaces, the facet pools, and the per-surface legs are *structural*, not just names; a name-only template cannot express "this corpus has four surfaces, that one has two", nor the per-surface membership/filter predicates.
- **Ship a bare Protocol and let each consumer reimplement the body.** Rejected — the RRF fusion, the `k` cap, the leg skeleton, the cycle guard, and the hop cap are invariant across corpora; forcing each consumer to re-author them throws away the reuse the library exists to provide.
- **A declarative descriptor consumed by a Protocol-paired ABC that owns the invariant skeleton (chosen).**

**Decision.**

Three load-bearing choices carry the seam.

**1. The corpus is declarative data.** `engram.ai.retrieval.schema` defines `CorpusSchema` (an ordered list of `SearchSurface`s — table, key/text/embedding columns, hit level, page-id and title expressions, join, membership, filters, BM25 index — plus `FacetPool`s, `Facet`s, the embedding SQL type, and `level_facet` naming the hit-level-gating facet) and `GraphSchema` (edge table + src/dst/rel columns, edge-payload columns, node view + columns, and `node_col_types`). The SQL is generated from these; the descriptor is the whole corpus-specific surface.

**2. The extension point pairs a Protocol contract with an ABC base (Template Method).** For search, `HybridSearchBuilder` (the Protocol) and `BaseHybridSearchBuilder` (the ABC) own the invariant shape — the facet-pool CTEs, the per-surface BM25 + vector legs, the RRF merge `sum(1.0 / (60 + r))`, the `k` cap `least(greatest(k, 1), 50)`, `SECURITY DEFINER`, and the RETURNS contract — with six dialect hooks for the BM25 grammar and the workaround shape (static-vs-dynamic outer form, materialisation, param style). `ParadeDBHybridSearchBuilder` and `PgTextSearchHybridSearchBuilder` are the two concrete builders. For graph, `GraphTraversalBuilder` + `BaseGraphTraversalBuilder` own the signatures, the RETURNS (from the descriptor), the hop/`k` caps, and the shared final projection, with `CteGraphTraversalBuilder` and `AgeGraphTraversalBuilder(graph_name)` owning the divergent traversal cores. This is the library-extension-point case in [design-patterns.md](../../../docs/explanation/design-patterns.md#descriptor-driven-sql-generation): the Protocol is the true contract, the ABC hands the consumer reuse, and a power user can still satisfy the Protocol from scratch.

**3. engram is one adapter.** engram supplies `WIKI_CORPUS_SCHEMA` (`features/serve/corpus_schema.py`) and `WIKI_GRAPH_SCHEMA` (`features/serve/graph_schema.py`) as data. Each dialect / backend class delegates body generation to the library builder fed its schema (`ParadeDBHybridSearchBuilder().api_search_body(WIKI_CORPUS_SCHEMA)`, `CteGraphTraversalBuilder().expand_body(WIKI_GRAPH_SCHEMA)`, …) and the verbatim SQL-body constants are deleted. No migration wiring changed: the api-surface migration (`0002`) already called `_dialect().api_search_body()` and the graph migration (`0004`) already iterated the backend's four methods, so the delegation seam the builders now sit behind was already the plug point.

Two supporting conventions: fragments that reference a facet carry a brace-delimited `{name}` placeholder, substituted per dialect by explicit `.replace` (positional `$N` vs named), never `str.format` — that would collide with the `$$`-quoting and brace-bearing SQL. And `GraphSchema.node_col_types` is carried explicitly because the graph RETURNS is **corpus-variable** (a corpus's node columns differ), unlike search's fixed RETURNS contract; an empty tuple means "all `text`", so engram declares `("text", "text", "text", "text", "boolean")` for its `(id, type, title, status, superseded)` node view.

**Consequences.**

- (+) **The corpus schema is data.** A new corpus is a `CorpusSchema` + `GraphSchema` value, not a SQL rewrite; the invariant RRF / cap / leg / cycle-guard skeleton lives once, in the ABC.
- (+) **engram serve is a thin adapter.** `search_dialect/` and `graph_backend/` hold engram's two descriptors plus a delegation to the library builder; the retrieval SQL no longer lives in engram at all.
- (+) **The DB-engine axis is preserved.** [ADR-0006](0006-dual-dialect-bm25-seam.md) and [ADR-0007](0007-age-multihop-dual-graph-backend.md) still select the dialect / backend. The builder is chosen the same way, so the `pg_textsearch` + AGE vs ParadeDB + CTE selection is unchanged.
- (−) **The generated SQL *text* differs from the hand-written originals.** No-regression is therefore proven behaviourally, not by text-identity — see [ADR-0036](0036-behavioral-parity-generated-sql.md). A reviewer reading the migration diff must not mistake the changed body text for a behavioural change.
- (−) **The descriptor must faithfully carry every schema-specific token.** It was authored against a full read of the real bodies so every literal (`wiki.edges`, the four surfaces, the pools, the payload column) has a home; a corpus that under-declares its schema gets wrong SQL, caught by the result-parity tiers.
- **Reversible?** Yes, additively. An adapter could re-inline a hand-written body for one dialect while the others stay generated; the descriptors and builders are purely additive to the existing dialect/backend seam.

**Wire-vocabulary retention (a Phase-3 review outcome).** The library's public result models keep a few engram-leaning field names as a deliberate, bounded retention: `SearchHit.hit_level` / `page_id` / `page_title`, `GraphEdge.provenance_claim`, and `Graph.page_type`. These are the stable frontend-zod + SQL-`RETURNS` contract, and the plan froze the `/api` surface (frontend unaffected, no `gen:types` churn), so the library treats them as opaque generic identifiers rather than renaming them and breaking the wire. The descriptor-authoring API a new consumer actually writes is domain-general (for example the surface attribute is `parent_id_expr`, not `page_id_expr`, even though the emitted column stays `page_id`); only the result-column names are the retained contract. A future initiative willing to version the `/api` contract (and regenerate the frontend types) can rename them end to end. Until then this is an accepted domain-purity trade-off, named here so a purity pass reads it as intentional rather than an oversight.
