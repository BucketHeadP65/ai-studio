# Product decisions (D-log): the contested choices and why

This is engram's **product / solution-design** decision log: every contested schema, vocabulary,
curation, and retrieval-doctrine choice, the side taken, and what was rejected. It is the *why*
behind the system described in [vision.md](vision.md). It is **append-only**, reversing a decision
gets a new entry, never an edit.

**Two altitudes of decision.** These `D-n` entries are *product* decisions (what the knowledge model
and its doctrine should be). The repository's **ADRs** ([engram/docs/adr/](../adr/)) are the
*engineering* decisions: how the code realizes them. The table below maps each product decision to the
engineering ADR (or the engine) that implements it. Read `D-n` for the rationale, then follow the link
to see how it is built. Migrated from the Knowledge knowledge base per [ADR-0013](../adr/0013-design-and-vision-docs-in-repo.md).

The log itself follows, verbatim and append-only. Format: **D-n: decision**, why, what we rejected.
Research grounding lives in [research/](research/) (`01–05`).

**D-1: Fixed backbone, open vocabularies.** The structure (3 layers, 7 page types, sections, claims, edges) is frozen across domains. Domain specifics live in the vocabulary (entity types, relations, facet values). *Why:* kills the per-domain schema agonizing. Agents discover vocabulary by querying the vocabulary, not by re-learning schemas. *Rejected:* per-domain page schemas (ORKG-style templates per research problem), power we don't need at the cost of agent legibility.

**D-2: Claims are block-anchored bullets in paper notes, not separate files.** `^cN` block ids + `key:: value` sub-bullets. *Why:* claims live with their provenance, stay Obsidian-addressable (`[[note#^c3]]`), avoid thousands of micro-files, and parse deterministically. *Rejected:* one-file-per-claim (nanopub-literal), correct but unusable for humans.

**D-3: Provenance over confidence, support is computed, not stored.** No numeric confidence anywhere. Claims carry loc + verbatim quote (scite lesson). Entity-level trust is a SQL aggregation over supports/refutes/outperforms edges, recomputed as evidence lands. The `api.scoreboard` view that served it was dropped in migration 0052, because it named one knowledge base's page types and claim kinds, so an agent aggregates `api.claims` itself. *Why:* stored confidence numbers are unauditable vibes that go stale. Computed support is self-updating and explainable. *Rejected:* FCVW-style confidence states (except the discrete claim `status`).

**D-4: Comparative claims require qualifiers.** `outperforms`/`comparable_to` without dataset/task + metric fails validation. *Why:* SciFact-Open's documented failure mode, evidence that holds only in a special case. Unqualified "X beats Y" is the silent-blend failure as an edge. Null results get a first-class relation (`comparable_to`) and page_type (`negative-result`) because pruning strategies later depends on them.

**D-5: Supersede, never delete, status is QA, supersession is temporal truth.** Two orthogonal mechanisms (synthadoc by LLM-Wiki-v3 composition). *Why:* the end goal is *pruning* RAG strategies. The graveyard and the why-pruned trail are products, not waste. Default SQL views filter superseded. History stays queryable.

**D-6: Contradictions: preserve both + flag, resolution = a comparison page.** Auto-resolve forbidden. *Why:* most RAG contradictions are condition-dependent. The resolution IS the conditions analysis, which is exactly what a comparison page documents.

**D-7: Canonical H2 vocabulary per page type, H2 = retrieval unit (≤ ~600 tokens).** Chunking is decided at write time by the author who understands the content. *Why:* same-shaped pages make sections comparable across the knowledge base (`WHERE canon='limitations'` over 50 papers). Breadcrumb-prefixed section embeddings get most of contextual retrieval for free. *Rejected:* algorithmic chunking of knowledge base pages at index time.

**D-8: The summary ladder (`summary` ≤400 chars to TL;DR ≤150 tok to sections).** Every page retrievable at three grains regardless of size. *Why:* absorbs document-size variance structurally (part of killing per-domain decisions). Cards make L1 scans ~50-150 tokens each.

**D-9: Collapsed multi-level search, never force tree descent.** Cards, sections, and claims share one hybrid index with a `level` column. Agents filter by level/facets when they want the ladder. *Why:* RAPTOR's collapsed-tree beat tree-traversal, and PageIndex-style forced traversal lost to flat agentic retrieval (arXiv 2511.18177). The ladder is a *protocol agents may use*, not a topology they must walk.

**D-10: Postgres target: PG17 + ParadeDB pg_search + pgvector 0.8 + ltree (self-hosted), tsvector fallback.** *Why:* one engine gives Lucene-style query strings, real BM25, snippets, facets, and SQL-composable hybrid (hand-written RRF). Typed columns (incl. text[] facets) for hot filters, small jsonb for long-tail. EAV and jsonb-GIN-everything are hostile to LLM-written SQL and the planner. *Caveat:* managed-PG availability of pg_search is narrowing (Neon dropped it), plan self-host. Keep the tsvector fallback documented.

**D-11: Agent surface = curated `api` schema: ≤ ~12 views, ≤100 columns total, base tables ungranted.** COMMENT ON everything (with example values), `api.schema_guide` meta-table with per-surface purpose + exemplar queries, `api.search()` / `api.lookup_value()` functions, read-only role + statement_timeout. *Why:* under ~100 columns agents can take the full annotated schema and skip schema-linking failures (BIRD/Spider 2.0 evidence). M-Schema-style content (descriptions + example values) beats raw DDL. Exemplar runbooks drove the biggest production gains.

**D-12: Write autonomy: free agent writes + mandatory log, no quarantine yet.** *Why:* personal knowledge base, single writer at a time, git/Sync history as revert path. Eval-gated `pending/` quarantine is deferred until multi-agent autonomous writes start (revisit then, that's the LLM-Wiki-v3 fork). *(Superseded by D-22: authoring is now programmatic + contract-validated, not free-write.)*

**D-13: Knowledge base layer is Markdown-canonical, the graph is a derived table.** Edges come only from typed frontmatter keys and claim fields. Postgres `edges` + recursive CTEs serve multi-hop. *Rejected:* a graph database, unproven payoff (failed adversarial verification in the llm-wiki survey), and "rebuildable from Markdown" stays absolute. *(Amended by D-23: Apache AGE added as a second in-Postgres backend, still a projection rebuilt from `kb.edges`.)*

**D-14: Zotero keys are the cross-system join.** `zotero_key` ties knowledge base paper notes ↔ raw mirrors ↔ Zotero items (incl. scite retraction checks). The knowledge base never duplicates reference management.

**D-15: Incremental re-indexing is not promised.** The indexer is an idempotent full rebuild (hash-gated re-embedding only). *Why:* honest. Incremental update is the least-solved part of the pattern (DeepWiki ships weekly full refresh). We optimize when the knowledge base makes full rebuilds painful.

**D-16: Retrieval routing is a living policy document, not code.** Question archetypes, then entry surface, then escalation, then budget, live in `retrieval-policy` (a knowledge base page: draftable, supersedable, linted), indexed into `api.about` so query agents read it at L0 and *decide*. *Why:* consumers are heavy agentic models that code/SQL natively. Doctrine beats classifiers. The policy compounds as usage evidence lands instead of freezing in code. *Rejected:* enforced `api.route()` (freezes strategy), per-agent skill doctrine (forks and never compounds. Skills get *indexed from* the policy later instead). (Grill session 2026-06-10.)

**D-17: Usage loop: telemetry is exhaust, knowledge is synthesis.** Query agents log every session to DB-side `kb.query_log` (via insert-only `api.log_session()`). The table is operational telemetry, disposable, never in the knowledge base, explicitly **exempt from the rebuild-from-Markdown invariant**. Answers cross into the knowledge base only as pages, rule-gated: an answer becomes/extends a `q.*` page iff it synthesized across ≥3 pages AND no existing page answers it. ≥3 related question pages means lint flags a concept/playbook candidate. A periodic usage digest (lint) flags hot-topics-without-playbooks, cold stubs (prune candidates), and orders refresh/verification by heat (DeepWiki lesson: don't maintain what nobody reads). The same data tunes `retrieval-policy` budgets. *Rejected:* auto-persisting every Q&A (noise), frontmatter usage counters (telemetry leaking into the authoring contract + sync churn). (Grill session 2026-06-10.)

**D-18: Map layer: authored MOC hubs + computed coverage, clustering deferred behind a trigger.** New page type `moc` (prefix `moc.`, `Wiki/Maps/`), **navigation, not knowledge**: curated hub pages grouping a topic's pages into sub-themes with one-liners. Promotion-gated: created only when lint flags ≥12 pages sharing a facet/theme with no covering map. Links inside a moc's `## Map` section index to `maps` edges (the one sanctioned body-link edge source, amendment to D-13). `api.coverage` (pure SQL: facets by type by counts by degree by freshness) shipped for "what do we know about X", and was dropped in migration 0052 because it named one knowledge base's facets. `api.facets` answers the same question. Algorithmic clustering (GraphRAG-style communities) is **deferred**, revisit when knowledge base > ~500 pages or hub maintenance lags (rising orphan rate despite hubs). Our research pass flagged auto-community payoff as unproven, and LazyGraphRAG's lesson is to defer expensive structure. Serves both directions: query agents get "start here". Ingest step 5 gets "which hubs must this paper compound into". (Grill session 2026-06-10.)

**D-19: Collections are a column, federation lives at the agent layer.** Multi-knowledge-base growth is logical first: a `collection` column (default `research`) on `pages`/`sources_raw`/`raw_chunks` (children inherit via FK), per-collection `purpose.md` + maps, shared-core registries. **Separate deployments of the same backbone only at isolation boundaries** (privacy/sharing/compliance, e.g. personal-health never co-resides with a shareable research knowledge base). Cross-knowledge-base "search everything" = the agent fans the same query out over N instances of the **identical `api.*` contract** and RRF-merges (DeepWiki MCP model). The fixed contract makes the gateway free. No SQL-level gateway service. Structural auto-evolution is rejected outright (contradicts D-1): the organism evolves content/vocabulary on a frozen backbone. *Written triggers:* physical partitioning by collection at >~5M embedded rows per instance. Cross-collection entity identity (same `ent.bm25` in two knowledge bases) is a known-hard open problem, deferred to `same_as` edges when it bites. (Grill session 2026-06-10.) **As-built ([ADR-0042](../adr/0042-corpus-qualified-identity.md)):** `collection` is now part of the composite primary key `(collection, id)` on every knowledge-base-owned table, not an ordinary column, and the `research` server-default is dropped. Children carry their own `collection` through composite foreign keys. The logical-first, isolation-boundary-deployment, and agent-layer-federation framing stands. The cross-collection entity-identity problem deferred here to `same_as` edges is now addressed by declared SKOS mapping relations (`exactMatch`/`closeMatch`/`broadMatch`/…), deliberately not `owl:sameAs`.

**D-20: CE budgets: hard floors, recommendation doctrine, telemetry audit.** Three tiers. (1) Infrastructure floors, judgment-free: read-only role, `statement_timeout=10s`, `api.search` caps `k≤50`, `api.fetch` truncates past ~8k tokens with an explicit steering notice, exemplars always `LIMIT`ed. These block only degenerate behavior. **As built ([ADR-0047](../adr/0047-the-agents-sql-is-checked-before-it-runs.md)):** `run_sql` checks every statement before it runs, the row cap runs inside the query, and every reader role waits at most five seconds for a lock. (2) Per-archetype budgets in `retrieval-policy` stay **non-binding**. Heavy agents may exceed them knowingly. (3) The teeth are the audit loop: `query_log.tokens_loaded`. Lint digest flags sessions at more than twice their archetype budget. Recurring overspend tunes the policy (budget was wrong) or tightens a floor (behavior was wrong). *Rejected:* hard mid-session metering (produces truncated, half-grounded answers. Fights the heavy-agent judgment model), per-archetype quotas in api functions (router-in-code through a bypass, contra D-16). (Grill session 2026-06-10.)

**D-21: Batch ingest = parallel extract + serialized merge (ownership partitioning, no locks).** Per-paper extraction (ingest steps 1-4) runs in isolated parallel workers, each owning exactly two files: the paper note (single-writer by construction, claims live with their provenance, so the parallelizable 90% of ingest has no shared state) and a transient staging manifest in `_meta/ingest-staging/` carrying everything that touches shared surfaces (entity proposals, facet rows, contradiction candidates, queue items). Shared surfaces (entity pages, registries, comparisons, maps, `log.md`) are written only by one serialized merge phase that consumes and deletes the manifests. Quote verification (`verify_quotes.py`, whitespace-normalized) gates each note's `synthesized` status inside the worker. Manifests are exhaust, not knowledge (D-17): deleted after merge, never indexed. Orchestration lives in the knowledge-base-local `ingesting-papers` workflow (`.claude/skills/`). *Why:* the contention surface is exactly the compounding step (5-6). Partitioning by ownership needs no lock primitive (none exists over a live-synced filesystem knowledge base) and scales linearly with papers. The merge becomes a Postgres transaction in the indexer. *Rejected:* fully sequential ingest (over-serializes. One context degrades across 4 long papers), per-entity file locks (no real primitive, deadlock-prone under Obsidian Sync), extractors editing entity pages directly (races exactly where evidence compounds). (Batch session 2026-06-10.)

**D-22: Knowledge base notes are constructed and validated programmatically, not hand-written prose.** Ingestion extractors no longer type the paper note's markdown by hand (the "blind trust" of D-12's free-write). Each extractor emits an `AuthoringPayload` JSON (typed frontmatter + section bodies + structured claim fields), and the engram app's note-grammar kernel renders + validates it into canonical `.md` before it touches disk: `studio note build` applies the claims grammar, checks registry vocabulary, and verifies every `quote::` against its `Sources/` mirror (whitespace/Unicode-normalized), writing atomically only on success. `studio note validate`/`verify` re-check an existing note. `studio note schema --type <pagetype>` emits the payload's JSON schema as the authoritative field list. The grammar is encoded once in a shared kernel (`src/wikinote/` in the `engram` app) consumed by two callers: the indexer parses it at index time, the authoring CLI constructs against it at write time. *Why:* **one schema, two consumers**: "validated files, not trusted prose" replaces blind-trust authoring with a contract-checked write path, so a note is well-formed (anchors, required `loc::`/`quote::`, comparative qualifiers, vocabulary) and quote-faithful *before* it lands, not after a separate validation pass. Reuses the parser the indexer already needs. The renderer owns the markdown shape so authors never reproduce it by hand. The change is to **who writes the files**, not to the grammar. `_meta/schema.md` (page types, frontmatter, canonical H2s, claims grammar, registry-validated vocabulary) is **unchanged**. This records that the binding contract is now mechanically enforced at construction. (Build session 2026-06-11.)

**D-23: Multi-hop is served by two interchangeable graph backends (recursive-CTE + Apache AGE), amends D-13.** D-13 kept the graph a derived table served by recursive CTEs and rejected a graph database. This adds **Apache AGE** (an *in-Postgres* openCypher extension) as a second multi-hop backend alongside the CTEs, not a replacement. Both implement one `GraphBackend` port (Strategy Registry, like the BM25 dialect seam) and serve the same two capabilities: **Expand** (seed to k-hop traversal along an optional relation-type filter) and **Paths** (ranked relational paths between two entities), each returning the subgraph + claim provenance for L4 verification. AGE's graph is a **projection rebuilt every indexing pass from `kb.edges`**. `kb.edges` stays the single source of truth, so D-13's two invariants hold: Markdown-canonical and rebuildable. Backend is config-selected (`APP_RETRIEVAL__GRAPH_BACKEND`, default `cte`). Surface is a dedicated `api.graph_expand`/`api.graph_paths` + MCP tools + a new retrieval-policy archetype, **opt-in and routed**, never fused into `api.search`. *Why:* the knowledge base's edges are *dense, curated, typed, qualified, claim-provenanced* (the regime where graph structure pays), and keeping both backends turns D-13's "unproven payoff" from an assumption into an empirical, golden-dataset comparison. Engineering ADR: [ADR-0007](../adr/0007-age-multihop-dual-graph-backend.md). (Plan session 2026-06-17.) **As built (2026-10-11, [ADR-0049](../adr/0049-graph-walks-keep-the-set-of-reached-nodes.md)):** both backends walk over the set of reached nodes, one hop at a time, from one generated function in which only the one-hop read differs, and `api.graph_reach` tells an agent that no route exists apart from a route longer than it searched.

**D-24: OKF is an export/interchange view, not a schema change.** Google's Open Knowledge Format (v0.1, Apache-2.0, a directory of Markdown files with YAML frontmatter + untyped links) formalizes the same LLM-wiki substrate this knowledge base uses, at a strict *subset* of our rigor (one required field `type`, prose-typed links, a single optional `timestamp`, no typed edges, no claim-level provenance, no supersession). We therefore treat OKF as an **interchange target, not an authoring contract.** (a) Add an `engram`-side OKF **export** that projects a collection into a conformant OKF export directory: one concept per page. Typed edges emitted as plain Markdown links **plus** a non-standard extension frontmatter key that preserves the relation type and claim provenance (OKF permits arbitrary keys and requires consumers to ignore unknowns, so the export directory stays conformant while we stay lossless). (b) An OKF **importer** is **deferred** behind a real need. *Why:* near-zero cost (we are already Markdown + frontmatter). Gives D-19 an at-rest, vendor-neutral wire format. Lets non-Postgres consumers use our knowledge. Banks the credibility of a hyperscaler endorsing the substrate. *Rejected:* adopting OKF as the authoring schema (discards the entire value-add, OKF is a floor, not a ceiling), ignoring OKF, waiting for v1.0. Full analysis in [okf.md](okf.md). **As built (2026-06-18):** the `engram export okf` command (reusing the indexer's parse + resolve, *not* an indexing stage, [ADR-0009](../adr/0009-okf-export-interchange.md)). The pinned extension-key convention is `okf_x_relations` (`{rel: [concept-id]}`) + `okf_x_engram` (id/status/collection/facets/aliases/supersession, papers add provenance), round-trip-tested, exporting 485 conformant concepts from the live knowledge base. (OKF research session 2026-06-18.)

**D-25: The page-type ontology is per-knowledge-base data, engram is distributed as a Claude Code plugin, amends D-1.** D-1 fixed 7 page types as a frozen cross-domain structure and rejected per-domain schemas. This amends the "7 page types frozen" clause only: the types are now per-knowledge-base data declared in a `KnowledgeBaseSchema` (`knowledge-base-schema.json` at the knowledge base root), validated by the indexing stage exactly as vocabulary is validated against `VocabularyIndex`. The *machinery and the single `api.*` agent contract* remain frozen: no per-knowledge-base Postgres tables, no runtime `create_model`, no M-Schema changes. The research 7+1 types become a bundled default `research` schema. The live knowledge base falls back to it when no `knowledge-base-schema.json` is present. Alongside the schema kernel, engram is shipped as a Claude Code plugin (`engram/plugin/`) that packages the retrieval MCP server and the `/knowledge-base:init` onboarding skill. The knowledge base carries no hardcoded engram paths. `studio init` is configure-only: given a reachable CLI and Postgres, it scaffolds `_meta/`, migrates the schema, and loads vocab. It does not provision DB or package engram for install. *Why:* engram was already ~95% domain-agnostic. The page-type layer was the only real coupling, removable at S-M cost confined to `wikinote/`. Any markdown knowledge base (cooking, legal, personal, company) is now a first-class engram knowledge base: install plugin, then `/knowledge-base:init`, then `knowledge-base-schema.json`, then `studio init`, then bundled skills and MCP work. *Rejected:* runtime `create_model` + per-knowledge-base Postgres columns (XL cost, invalidates the fixed agent contract, the path D-1 originally closed), auto-provisioning DB (out of scope for a plugin), a SessionStart auto-onboard hook (no first-install hook in Claude Code). Engineering ADR: [ADR-0014](../adr/0014-domain-general-vault-spec-and-plugin.md). (Generalization session 2026-06-20.)

**Open / deferred:** git init for the knowledge base, MCP serving of the three interfaces (structure/content/ask), indexing `battle-tested` playbooks into agent skills. *(The eval harness, once "open", is now built, see [eval-loop.md](eval-loop.md).)*
